## 1. Інфраструктура як код

**Infrastructure as Code (IaC)** — підхід, за якого інфраструктуру та її конфігурацію описують файлами, що зберігаються, перевіряються й змінюються подібно до програмного коду. Замість незафіксованих ручних дій команда отримує повторюваний опис бажаного результату.

IaC може охоплювати різні рівні:

| Рівень | Що описують | Приклад результату |
|---|---|---|
| Хмарні ресурси | мережі, віртуальні машини, балансувальники, сховища, дозволи | відтворюване середовище в хмарі |
| Операційна система | пакети, користувачі, служби, файли конфігурації | узгоджений стан серверів |
| Застосунок | версії, параметри запуску, залежності, конфігураційні файли | передбачуваний запуск застосунку |
| Контейнерна платформа | сервіси, репліки, мережі, політики розгортання | відтворюваний опис робочого навантаження |

IaC — загальна практика, а не назва одного інструмента. Один проєкт може використовувати кілька засобів: наприклад, provisioning-інструмент створює віртуальні машини, а configuration-management-інструмент налаштовує на них операційну систему й застосунок.

### 1.1. Основні принципи

- **Декларативність:** описують кінцевий бажаний стан, а не лише послідовність ручних кроків.
- **Повторюваність:** однаковий опис у контрольованому середовищі має приводити до очікуваного результату.
- **Ідемпотентність:** повторне застосування опису, коли система вже відповідає вимогам, не повинно спричиняти зайвих змін.
- **Контроль версій:** зміни коду можна переглядати, порівнювати, погоджувати й повертати.
- **Перевірюваність:** структуру та зміни можна перевіряти до застосування.
- **Модульність:** спільні налаштування варто повторно використовувати через ролі, модулі або компоненти.
- **Безпечні зміни:** доступи обмежують, секрети не зберігають у відкритому вигляді, зміни проходять review.

### 1.2. Декларативний та імперативний підходи

**Імперативний підхід** описує дії та їх порядок: встановити пакет, відредагувати файл, перезапустити службу. Він корисний для процедур, де важливий конкретний алгоритм, але повторний запуск може зробити зайві зміни або завершитися помилкою, якщо початковий стан відрізняється від очікуваного.

**Декларативний підхід** описує бажаний стан: пакет має бути встановлений, служба — увімкнена, файл — містити визначені параметри. Інструмент зіставляє фактичний стан із бажаним і виконує потрібні зміни.

Багато інструментів поєднують обидва підходи. Навіть декларативний опис не гарантує автоматичної безпеки чи відсутності помилок: потрібно розуміти план змін, залежності, права доступу й наслідки застосування.

### 1.3. Configuration management і provisioning

**Provisioning** створює або виділяє ресурси: віртуальну машину, мережу, диск, облікові записи хмарного сервісу. **Configuration management** налаштовує вже доступний вузол або сервіс: пакети, користувачів, служби, шаблони конфігурації та стан застосунків.

Межа не завжди абсолютна. Деякі платформи мають функції кількох категорій, а автоматизаційні конвеєри з'єднують інструменти різних рівнів. Важливо класифікувати інструмент за основним завданням, а не лише за тим, що його конфігурацію записують кодом.

```text
Запит на середовище
        │
        ▼
Provisioning: створення мережі та вузлів
        │
        ▼
Configuration management: налаштування ОС і служб
        │
        ▼
Deployment: розгортання застосунку
        │
        ▼
Перевірка, моніторинг і подальше узгодження стану
```

### 1.4. Переваги, ризики й обмеження

**Переваги:** швидше відтворення середовищ, узгодженість вузлів, прозорі зміни, простіший аудит і менша залежність від ручної пам'яті.

**Ризики:** помилка в шаблоні може вплинути на багато ресурсів; надмірні привілеї автоматизації збільшують наслідки компрометації; секрети можуть потрапити в репозиторій або журнали; зміни можуть спричинити простої чи втрату даних.

Для зменшення ризиків застосовують перевірку змін, найменші необхідні привілеї, захищене керування секретами, розділення середовищ, резервне копіювання та контрольований процес відкату. IaC не замінює архітектурного review, тестування, моніторингу або плану відновлення.

## 2. Ansible для управління конфігурацією

**Ansible** — інструмент автоматизації, який часто використовують для управління конфігурацією серверів, розгортання застосунків і виконання операційних задач. У типовій архітектурі Ansible працює з control node та керованими вузлами через SSH для Linux або відповідний механізм підключення для інших платформ. Для типового керування Linux-вузлами окремий постійний агент Ansible на цільовому вузлі не потрібен.

| Поняття | Значення |
|---|---|
| **Control node** | Середовище, з якого запускають Ansible та зберігають automation-проєкт. |
| **Managed node** | Вузол, конфігурацією якого керує Ansible. |
| **Inventory** | Перелік вузлів або груп, на які спрямовується автоматизація. |
| **Playbook** | YAML-опис одного або кількох plays для заданих хостів. |
| **Task** | Окрема декларація потрібної операції. |
| **Module** | Компонент, який виконує типову дію: керує пакетом, файлом, користувачем чи службою. |
| **Handler** | Дія, що запускається у відповідь на зміну, наприклад перезапуск служби після оновлення конфігурації. |
| **Role** | Повторно використовувана структура задач, змінних, файлів і шаблонів для певної функції. |

Спрощена схема роботи:

```text
Inventory визначає цілі
         │
         ▼
Playbook задає plays і tasks
         │
         ▼
Модулі перевіряють та узгоджують стан вузлів
         │
         ▼
Звіт про успіхи, зміни та помилки
```

### 2.1. Як читати playbook

Нижче наведено **ілюстративний фрагмент для читання**, а не команду для запуску. Він показує бажаний стан: пакет NGINX встановлено, а служба увімкнена й працює. Точний синтаксис і параметри залежать від версії Ansible та цільової платформи.

```yaml
- name: Configure a web server
  hosts: web
  become: true
  tasks:
    - name: Ensure NGINX is installed
      ansible.builtin.package:
        name: nginx
        state: present

    - name: Ensure NGINX is running and enabled
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true
```

Під час читання зверніть увагу:

1. `hosts` визначає цільову групу з inventory.
2. `become` запитує підвищення привілеїв для задач, яким вони потрібні; його не слід вмикати без необхідності.
3. Модулі `package` та `service` описують стани, а не ручний набір команд операційної системи.
4. `state: present` і `state: started` мають узгодити вузол із вимогою.
5. Playbook не задає облікові дані, тому що секрети не потрібно вбудовувати в приклад чи зберігати відкрито у репозиторії.

### 2.2. Ідемпотентність і звіт про зміни

Ansible-модулі зазвичай прагнуть ідемпотентного результату: встановлення вже встановленого пакета або забезпечення вже запущеної служби не має створювати зайву зміну. У звіті Ansible розрізняє задачі, які змінили вузол, виконалися без зміни або завершилися помилкою. Окремі модулі чи довільні shell-команди можуть не мати ідемпотентної поведінки автоматично, тому результат повторного запуску потрібно аналізувати.

### 2.3. Практики безпечного використання

- Зберігайте playbook та ролі у контрольованому репозиторії, але не додавайте до нього паролі, приватні ключі чи токени.
- Для секретів використовуйте призначене захищене сховище або механізм шифрування секретів; обмежуйте тих, хто може їх розшифрувати.
- Надавайте control node лише потрібний мережевий доступ і найменші необхідні привілеї.
- Визначайте цільові групи явно; не запускайте зміни на ширшому наборі вузлів, ніж потрібно.
- Перевіряйте зміни на тестових вузлах перед широким застосуванням.
- Враховуйте, що звіти й журнали запуску також можуть містити чутливу інформацію.

## 3. Сучасні інструменти управління конфігурацією

Інструменти відрізняються мовою опису, способом підключення, архітектурою, екосистемою та основним призначенням. Вибір залежить від кількості вузлів, цільових ОС, доступності мережі, вимог до аудиту, навичок команди й моделі експлуатації.

| Інструмент | Типовий підхід | Характерні особливості |
|---|---|---|
| **Ansible** | Переважно push; керування часто без постійного агента | Playbook у YAML, inventory та модулі; поширений для налаштування серверів і автоматизації задач. |
| **Puppet** | Переважно pull у типовій агентній архітектурі | Каталог бажаної конфігурації зазвичай застосовується агентом; орієнтований на постійне узгодження стану. |
| **Chef** | Агентний підхід у типовій архітектурі | Рецепти описують конфігурацію; автоматизація виражається Ruby DSL. |
| **Salt** | Підтримує різні режими керування, включно з агентними та віддаленим виконанням | Сильні можливості централізованої автоматизації, подій і керування групами вузлів. |
| **CFEngine** | Агентний підхід і постійне узгодження політик | Підходить для керування великою кількістю вузлів із компактним описом політик. |

Назви режимів **push** і **pull** описують типовий напрямок ініціювання керування, а не всі можливості продукту. Реальні архітектури залежать від налаштування та версії.

### 3.1. Інструменти суміжних категорій

Не всі інструменти IaC є інструментами конфігураційного керування:

| Категорія | Приклади | Основне завдання |
|---|---|---|
| Provisioning та IaC | Terraform, OpenTofu, AWS CloudFormation | Опис і створення хмарних або інфраструктурних ресурсів. |
| Configuration management | Ansible, Puppet, Chef, Salt, CFEngine | Налаштування й узгодження стану вузлів та їхніх компонентів. |
| Образи та незмінна інфраструктура | Packer та подібні засоби | Створення підготовлених образів систем для подальшого розгортання. |
| Оркестрація контейнерів | Docker Swarm, Kubernetes | Планування та керування контейнерними робочими навантаженнями. |

Категорії можуть перетинатися в ширших платформах та конвеєрах. Наприклад, Terraform може створити віртуальну машину, після чого Ansible налаштує її ОС. Docker Swarm керує бажаним станом контейнерного сервісу, але сам по собі не є універсальною заміною управлінню конфігурацією операційної системи.

## Самостійна робота: інструменти управління конфігурацією

Робота виконується письмово за матеріалом лекції. Нічого не встановлюйте й не запускайте у спільному або хмарному середовищі.

### Завдання 1. Ansible для управління конфігурацією

Для наведеного вище прикладу playbook:

1. Визначте control node, керовані вузли, inventory, play, hosts, tasks і модулі.
2. Своїми словами опишіть бажаний кінцевий стан вузла після виконання обох задач.
3. Поясніть, чому повторне застосування такого опису в незмінному середовищі має бути ідемпотентним.
4. Назвіть, які права потрібні для встановлення пакета та керування службою і чому їх слід обмежувати.
5. Запропонуйте, коли потрібен handler і чому перезапуск служби не варто виконувати безумовно після кожного запуску.
6. Поясніть, де зберігати секрети підключення та як не допустити їх потрапляння у Git і журнали.

### Завдання 2. Порівняння популярних інструментів

Заповніть порівняльну таблицю для Ansible, Puppet, Chef і Salt:

| Критерій | Ansible | Puppet | Chef | Salt |
|---|---|---|---|---|
| Типова модель керування | | | | |
| Чи потрібен постійний агент у типовому сценарії | | | | |
| Основна форма опису конфігурації | | | | |
| Приклад доречного сценарію | | | | |
| Що потрібно перевірити перед вибором | | | | |

Додайте коротке пояснення, чому Terraform або CloudFormation не слід без уточнень називати прямими аналогами Ansible для налаштування пакетів і служб усередині ОС.

### Завдання 3. Вибір інструмента для сценарію

Для кожного сценарію оберіть інструмент або категорію інструментів і обґрунтуйте відповідь у 2–3 реченнях:

1. Створити VPC, підмережі та віртуальні машини у хмарі з можливістю переглядати зміни в Git.
2. Підтримувати встановлений пакет і конфігурацію служби на групі Linux-серверів.
3. Створити стандартизований базовий образ віртуальної машини.
4. Підтримувати бажану кількість реплік контейнерного застосунку.

Для кожного сценарію назвіть один ризик автоматизації та спосіб його зменшення.

## Підсумок лекції

IaC перетворює ручні інфраструктурні процедури на контрольовані та відтворювані описи. Provisioning створює ресурси, configuration management узгоджує стан вузлів, а оркестрація керує робочими навантаженнями. Ansible є одним із засобів керування конфігурацією; інші інструменти мають власні архітектурні моделі та сфери застосування. Надійна автоматизація потребує review, перевірки змін, захисту секретів і контрольованих привілеїв.
