# Заняття 4.3. Початкова робота з Terraform
### Змістовний модуль 4 · Infrastructure as Code

> **Тип заняття:** практичне.
>
> **Тривалість:** 120 хвилин.
>
> **Формат:** курсант самостійно встановлює Terraform на Linux, читає конфігурацію провайдера, ініціалізує робочий каталог та формує план. Навчальні приклади передбачають лише `plan`: створювати ресурси командою `apply` без окремого дозволу викладача не можна.

## Навчальні питання

1. Встановлення Terraform на ОС Linux.
2. Конфігурація провайдера.
3. Створення плану для розгортання інфраструктури відповідного провайдера.

## Мета заняття

Після роботи курсант може:

- перевірити системні вимоги та встановити Terraform CLI з офіційного репозиторію для підтримуваного Linux;
- пояснити призначення `required_version`, `required_providers` і блоку `provider`;
- безпечно надати провайдеру доступ до AWS або Proxmox без запису секретів у код;
- виконати `terraform fmt`, `init`, `validate` та `plan`;
- прочитати план і визначити ресурси, які Terraform пропонує створити, змінити або видалити;
- пояснити призначення state і lock-файлу та чому AWS і Proxmox приклади мають незалежні робочі каталоги.

Приклади розміщено в окремих каталогах:

```text
Lesson4_3/
├── README.md
├── .gitignore
└── examples/
    ├── aws/
    └── proxmox/
```

Оберіть **один** провайдер для виконання роботи. Це навчальні приклади планування, не готова production-інфраструктура. Не зберігайте у Git токени Proxmox, AWS access keys, паролі, приватні ключі, `.tfstate` або файли з реальними значеннями доступу.

### Вимоги для AWS

- AWS-акаунт і права, надані викладачем; передусім використовуйте AWS Academy Learner Lab, якщо він є навчальним середовищем курсу.
- Налаштований профіль AWS CLI або інший підтримуваний AWS credential provider.
- Вибраний регіон і доступ до потрібного API. Terraform plan для AWS-прикладу звертається до AWS і потребує чинних облікових даних.
- Назва S3 bucket має бути глобально унікальною. Зразок використовує `bucket_prefix`, але план однаково варто перевірити перед будь-яким застосуванням.

### Вимоги для Proxmox

- Доступний Proxmox VE API та обліковий запис або API-токен із мінімально необхідними правами.
- Готовий template VM, до якого має доступ токен, та його ID.
- Ім'я вузла Proxmox і вільний VM ID, погоджений з адміністратором.
- Terraform CLI 1.6 або новіший для актуальної версії провайдера `bpg/proxmox`.

Не використовуйте production Proxmox-кластер або чужий AWS-акаунт для експериментів. Уточніть у викладача доступні ресурси, ліміти та політику cleanup.

## 1. Встановлення Terraform на Linux

Для Debian або Ubuntu використовуйте офіційний APT-репозиторій HashiCorp. Команди додають підписаний ключ та джерело пакетів; не завантажуйте невідомі бінарні файли з випадкових сайтів.

```bash
sudo apt-get update
sudo apt-get install -y ca-certificates gnupg lsb-release wget
wget -O- https://apt.releases.hashicorp.com/gpg \
  | gpg --dearmor \
  | sudo tee /usr/share/keyrings/hashicorp-archive-keyring.gpg >/dev/null
echo "deb [signed-by=/usr/share/keyrings/hashicorp-archive-keyring.gpg] https://apt.releases.hashicorp.com $(. /etc/os-release && echo "$VERSION_CODENAME") main" \
  | sudo tee /etc/apt/sources.list.d/hashicorp.list
sudo apt-get update
sudo apt-get install terraform
```

Перевірте встановлення:

```bash
terraform version
```

На іншому дистрибутиві Linux скористайтеся інструкцією для відповідного пакетного менеджера на сторінці [Install Terraform](https://developer.hashicorp.com/terraform/install). Перевірте, що архітектура пакета відповідає системі, а Terraform доступний у `PATH`.

## 2. Terraform і провайдери

Terraform-конфігурація записується мовою HCL у файлах `.tf`. Зазвичай конфігурація визначає:

| Блок | Призначення |
|---|---|
| `terraform` | Версію Terraform та потрібні провайдери з обмеженнями версій. |
| `provider` | Параметри підключення до конкретного API, наприклад AWS-регіон. |
| `resource` | Ресурс, яким Terraform має керувати. |
| `variable` | Вхідне значення, яке можна передати без жорсткого кодування в ресурсі. |
| `output` | Значення, яке Terraform показує після успішного застосування. |

**Провайдер** — плагін, що перекладає конфігурацію Terraform у запити до API платформи. Назва провайдера сама по собі не створює інфраструктуру: це робить конфігурація `resource`, коли її застосовують.

Кожен зразок має власний робочий каталог і власний state. Не копіюйте state одного провайдера до іншого каталогу та не виконуйте `terraform init` із кореня репозиторію.

### Базовий цикл роботи

```bash
terraform fmt -check
terraform init
terraform validate
terraform plan
```

- `fmt` приводить HCL до стандартного форматування. Якщо перевірка виявила форматувальні зміни, виконайте `terraform fmt`.
- `init` завантажує потрібні провайдери та створює lock-файл `.terraform.lock.hcl` із вибраними версіями.
- `validate` перевіряє синтаксис і внутрішню узгодженість конфігурації; сам по собі цей крок не підтверджує доступ до API.
- `plan` порівнює конфігурацію з відомим state та актуальною інформацією провайдера й показує запропоновані дії. Планування може звертатися до облікового запису провайдера, але не виконує ці зміни.

План — це перевірка перед зміною, а не гарантія успіху майбутнього застосування: стан ресурсів або права можуть змінитися після його формування. Перед будь-яким `apply` потрібно переглянути план і отримати дозвіл.

## 3. AWS: конфігурація та план

Приклад у [`examples/aws`](./examples/aws) описує S3 bucket з навчальним префіксом. S3 вибрано для короткого першого прикладу: він не потребує SSH-ключа чи вибору типу віртуальної машини. Створювати bucket усе одно можна лише за окремим дозволом.

Перейдіть у каталог AWS-прикладу:

```bash
cd Lesson4_3/examples/aws
```

Надайте AWS credentials через профіль AWS CLI, AWS IAM Identity Center/SSO або погоджений механізм середовища. **Не** додавайте access key і secret key у `.tf` чи `.tfvars`.

```bash
aws sts get-caller-identity
```

Команда має підтвердити, що активний саме навчальний акаунт. Якщо використовується окремий AWS CLI profile, виберіть його за правилами навчального середовища, наприклад через `AWS_PROFILE`.

Перевірте й сформуйте план:

```bash
terraform fmt -check
terraform init
terraform validate
terraform plan
```

У плані для чистого стану очікується дія `create` для `aws_s3_bucket.lesson`. Переконайтеся, що регіон і префікс відповідають вимогам курсу. Не виконуйте `terraform apply` у межах цієї роботи.

## 4. Proxmox: конфігурація та план

Приклад у [`examples/proxmox`](./examples/proxmox) описує клонування наявного template VM у нову віртуальну машину. Для нього потрібні доступ до API та реальні значення вузла, VM ID і template ID. Не запускайте план проти системи, до якої вам не надали доступ.

Заповніть локальний файл параметрів із прикладу:

```bash
cd Lesson4_3/examples/proxmox
cp terraform.tfvars.example terraform.tfvars
```

Відредагуйте локальний `terraform.tfvars`: задайте адресу Proxmox API, ім'я вузла, унікальний VM ID та ID template, доступного для клонування. Файл `terraform.tfvars` ігнорується Git. API-токен передайте через захищений механізм секретів у змінну `TF_VAR_proxmox_api_token`; не вписуйте токен у команду, репозиторій чи скриншот термінала. На Linux можна попередньо отримати значення від викладача та передати його через захищений менеджер секретів або локальну сесію, не зберігаючи у файлах репозиторію.

Для інтерактивного навчального середовища токен можна ввести приховано в поточній Bash-сесії:

```bash
read -rsp "Proxmox API token: " TF_VAR_proxmox_api_token
export TF_VAR_proxmox_api_token
printf '\n'
```

Після завершення планування видаліть змінну з поточної сесії командою `unset TF_VAR_proxmox_api_token`. У спільному або автоматизованому середовищі використовуйте погоджений секрет-менеджер замість ручного введення.

Сформуйте план:

```bash
terraform fmt -check
terraform init
terraform validate
terraform plan
```

У плані очікується створення `proxmox_virtual_environment_vm.lesson`. Перевірте VM ID, вузол, джерело-клон і конфігурацію ресурсів. Не виконуйте `terraform apply` без окремого дозволу адміністратора: воно створить VM і використає ресурси Proxmox.

Якщо доступу до Proxmox API немає, виконайте `fmt`, `init` і `validate`, а план розберіть за підготовленим викладачем прикладом. Не підміняйте реальний успішний plan вигаданим виводом.

## Завдання практичної роботи

1. Перевірте ОС, архітектуру та наявність прав для встановлення Terraform.
2. Встановіть Terraform з офіційного джерела та покажіть результат `terraform version`.
3. Оберіть AWS або Proxmox; не підключайтеся до обох платформ без потреби.
4. Прочитайте `required_version`, `required_providers`, `provider`, змінні та ресурс у відповідному прикладі.
5. Надайте доступи без секретів у Git; для AWS підтвердьте акаунт, для Proxmox використовуйте видані вузол і template.
6. Виконайте `terraform fmt -check`, `terraform init`, `terraform validate` і `terraform plan`.
7. Поясніть кожну заплановану дію та покажіть, що `plan` не створив ресурс.
8. Збережіть `.terraform.lock.hcl` разом із навчальним кодом, якщо приклад переноситься до власного проєкту. Не зберігайте state та секрети.

## Критерії оцінювання

| № | Результат | Бали |
|---|---|---:|
| 1 | Встановлює Terraform з офіційного джерела та демонструє версію | 1 |
| 2 | Пояснює призначення Terraform-блоків і обраного провайдера | 1 |
| 3 | Коректно налаштовує AWS або Proxmox доступ без секретів у Git | 1,5 |
| 4 | Успішно виконує `fmt`, `init` і `validate` | 1,5 |
| 5 | Формує план і правильно пояснює заплановані дії та їх наслідки | 2 |
| 6 | Пояснює різницю між `plan` та `apply`, роль state і lock-файлу | 1 |
| | **Разом** | **8** |

Якщо навчальний доступ до провайдера недоступний, пункт плану перевіряється за погодженим прикладом викладача; курсант має чітко розрізняти локальну перевірку конфігурації та справжній план, отриманий від API.

## Контрольні питання

1. Для чого Terraform потрібен provider?
2. Чим `terraform init` відрізняється від `terraform validate`?
3. Яку інформацію показує `terraform plan`?
4. Чи створює `terraform plan` AWS bucket або Proxmox VM?
5. Чим state відрізняється від конфігураційних `.tf` файлів?
6. Навіщо Terraform створює `.terraform.lock.hcl`?
7. Де зберігати AWS credentials і Proxmox API token?
8. Які наслідки можуть мати `terraform apply` та `terraform destroy`?

## Прибирання та безпека

Це заняття завершується на етапі плану. Не запускайте `apply` або `destroy`, якщо викладач явно не доручив це в окремій контрольованій роботі.

Після завершення:

- перевірте, що локальні `terraform.tfvars`, `.tfstate*` та `.terraform/` не додані до Git;
- збережіть `.terraform.lock.hcl`, якщо він був створений для каталогу-прикладу;
- не видаляйте чужий чи спільний state і не відкликайте спільні доступи;
- видаліть тимчасові локальні credentials лише відповідно до правил навчального середовища.
