- спостерігати за станом вузлів, сервісу й задач командами Docker;

## Необхідні умови

- Запущений Docker Engine або Docker Desktop і доступна команда `docker`.
- Для демонстрації сервісу достатньо одного manager-вузла. Це показує оркестрацію задач, але не стійкість до втрати вузла.
- Для демонстрації розподілу задач потрібен багатовузловий кластер; заздалегідь перевірте, що вузли мають стан `Ready`.
- У реальному кластері між вузлами потрібні TCP `2377`, TCP/UDP `7946` і UDP `4789`. Дозволяйте цей трафік лише між вузлами кластера, не виставляйте його у публічний інтернет.
- Демонстраційний стек використовує NGINX з Docker Hub, не збирає власний образ і публікує HTTP-порт `8090`.

Перед заняттям переконайтеся, що порт `8090` не зайнятий і Docker Engine, до якого під'єднаний CLI, є навчальним. Не розгортайте демонстраційний стек у чужому або production Swarm.

## 1. Архітектура Docker Swarm

Docker Swarm — режим оркестрації, вбудований у Docker Engine. Кластер складається з вузлів:

| Роль або компонент | Призначення |
|---|---|
| **Manager** | Приймає команди керування, зберігає стан кластера, планує задачі та підтримує узгодженість між менеджерами. |
| **Worker** | Приймає призначені задачі й запускає контейнери сервісів. |
| **Service / сервіс** | Опис бажаного стану застосунку: образ, кількість реплік, порти та політики розгортання. |
| **Task / задача** | Призначений вузлу екземпляр роботи сервісу; Swarm створює для нього контейнер. |
| **Routing mesh** | Дає змогу звертатися до опублікованого порту через вузол кластера, перенаправляючи трафік до задачі сервісу. |

```text
docker stack deploy
        │
        ▼
   Manager (бажаний стан: 3 репліки)
        │ планує задачі
   ┌────┴───────────────┐
   ▼                    ▼
Worker 1             Worker 2
task 1, task 2       task 3
   │                    │
container             container
```

У кластері з одним вузлом усі задачі розміщуються на ньому. Кілька реплік не захищають від втрати цього вузла. У багатовузловому Swarm потрібна доступність менеджерського кворуму для зміни стану кластера; для production зазвичай використовують непарну кількість менеджерів, наприклад три.

## 2. Процеси у Swarm: від бажаного стану до задач

Swarm працює за моделлю узгодження стану. Адміністратор задає бажану конфігурацію сервісу, а manager порівнює її з фактичним станом і призначає задачі доступним вузлам. На вузлі worker агент отримує призначення та запускає контейнер. Якщо задача завершується, а кількість активних реплік стає меншою за бажану, manager планує заміну.

```text
Опис сервісу → manager планує task → worker запускає container
      ▲                                            │
      └──────── manager узгоджує стан ◄────────────┘
```

У виводі `docker service ps` можна побачити вузол задачі та її стан. Для аналізу викладач звертає увагу на:

- скільки реплік сервіс бажає і скільки реально працює;
- на яких вузлах розміщені задачі;
- чи є старі задачі зі станом `Shutdown`, `Failed` або іншим завершальним станом;
- чи з'явилася нова задача, коли змінено кількість реплік або завершено контейнер.

Окремий рядок старої завершеної задачі не обов'язково означає помилку: Swarm зберігає історію задач. Головна перевірка — актуальний стан сервісу та наявність потрібної кількості активних задач.

### Команди для спостереження

```bash
docker node ls
docker stack services lesson10
docker service ps lesson10_web
docker service inspect --pretty lesson10_web
docker service logs --tail 10 lesson10_web
```

`docker node ls` виконується на manager. Перегляд `docker service ps` та `docker stack services` показує стан оркестрації, а не лише локальні контейнери поточного вузла.

## 3. Демонстрація викладача

### 3.1. Перевірка та створення кластеру

Перейдіть до каталогу заняття та перевірте Docker:

```bash
cd Lesson2_10
docker version
docker info --format '{{.Swarm.LocalNodeState}}'
```

Якщо стан — `inactive` і це окреме навчальне середовище, створіть Swarm:

```bash
docker swarm init
docker node ls
```

Поточний вузол має показати стан `Ready` і роль manager/leader. Якщо середовище вимагає явну адресу вузла, задайте адресу, доступну іншим вузлам:

```bash
docker swarm init --advertise-addr <IP-адреса-менеджера>
```

Якщо Swarm уже активний, не запускайте `docker swarm init` повторно. Перевірте, що це навчальний кластер, та домовтеся з його адміністратором про дозвіл на демонстрацію.

Для пояснення приєднання worker викладач може показати команду отримання join-токена:

```bash
docker swarm join-token worker
```

Токен є секретом доступу до кластеру: не виводьте його на проєктор, не копіюйте у звіт і не публікуйте. Для реального приєднання worker команду `docker swarm join ...` виконують на самому worker-вузлі. Після цього на manager перевіряють `docker node ls`.

### 3.2. Перевірка опису та розгортання сервісу

Покажіть курсантам [stack.yaml](./stack.yaml) і попросіть перед запуском передбачити кількість задач, порт та ім'я сервісу. Перевірте злиту конфігурацію і розгорніть стек:

```bash
docker stack config --compose-file stack.yaml
docker stack deploy --compose-file stack.yaml lesson10
```

Покажіть склад стека й дочекайтеся трьох реплік:

```bash
docker stack services lesson10
docker service ps lesson10_web
docker service inspect --pretty lesson10_web
```

Очікуваний стан сервісу — `3/3`. У кластері з кількома вузлами зверніть увагу на розподіл задач у колонці `NODE`. У одно-вузловому середовищі всі репліки будуть на тому самому вузлі.

Перевірте доступ до NGINX:

```bash
curl --fail http://localhost:8090/
```

Відкрийте `http://localhost:8090` у браузері. Поясніть, що порт `8090` опублікований сервісом, а routing mesh приймає запит на вузлі кластера та передає його задачі сервісу. Порт може бути доступний на інших вузлах кластера згідно з налаштуванням ingress.

### 3.3. Масштабування та узгодження бажаного стану

До запуску команд запитайте аудиторію, скільки задач очікується після зміни кількості реплік. Змініть масштаб і перевірте фактичний стан:

```bash
docker service scale lesson10_web=5
docker stack services lesson10
docker service ps lesson10_web
```

Після демонстрації поверніть початкову кількість реплік:

```bash
docker service scale lesson10_web=3
docker stack services lesson10
docker service ps lesson10_web
```

Обговоріть, що команда змінює бажаний стан сервісу, а Swarm створює або зупиняє задачі, щоб привести фактичний стан до нього.

### 3.4. Відновлення після завершення задачі

Покажіть активні задачі та виберіть ту, контейнер якої буде завершено:

```bash
docker service ps lesson10_web
```

На вузлі, вказаному для вибраної задачі в колонці `NODE`, знайдіть її контейнер:

```bash
docker ps --filter label=com.docker.swarm.service.name=lesson10_web
```

Завершіть лише контейнер власного демонстраційного сервісу, підставивши його ID:

```bash
docker kill <container-id>
```

Якщо задача запущена на іншому вузлі, команди `docker ps` і `docker kill` треба виконати саме на ньому: локальний Docker CLI бачить контейнери тільки під'єднаного Engine. Спостерігайте на manager за відновленням:

```bash
docker service ps lesson10_web
docker stack services lesson10
curl --fail http://localhost:8090/
```

Поясніть: Swarm додає нову задачу, щоб повернутися до трьох реплік. Це демонструє відновлення після завершення контейнера, а не відмовостійкість до втрати вузла.

## Спільний аналіз аудиторії

Після кожного етапу курсанти за виводом команд відповідають:

1. Хто приймає команду `docker stack deploy` і хто запускає контейнер задачі?
2. Де побачити бажану кількість реплік, фактичний стан і вузол розміщення задачі?
3. Чому стара задача може залишатися у списку після того, як нова вже працює?
4. Що зміниться під час масштабування сервісу з трьох реплік до п'яти?
5. Яка різниця між завершенням контейнера однієї задачі та втратою вузла з усіма його задачами?
6. Чому три репліки на одному вузлі не забезпечують стійкість до відмови цього вузла?

## Підсумок заняття

Ключові висновки:

- Swarm оркеструє сервіси на основі заданого бажаного стану.
- Сервіс може мати кілька задач; кожна задача запускається як контейнер на призначеному вузлі.
- Manager керує станом і плануванням, worker виконує призначені задачі.
- Swarm намагається відновити бажану кількість задач після завершення контейнера.
- Масштабування змінює бажану кількість реплік; фактичні задачі створює та зупиняє оркестратор.
- Кількість реплік сама по собі не гарантує стійкість до втрати вузла або кворуму.

## Прибирання демонстраційних ресурсів

Після завершення видаліть лише стек цього заняття:

```bash
docker stack rm lesson10
docker stack services lesson10
```

Перевірте, що сервіс зник зі списку. Не виконуйте `docker swarm leave --force` на спільному, наданому або production-вузлі. Для окремого одноразового навчального Swarm залишайте його лише за погодженням із викладачем.
