>
> **Тривалість:** 120 хвилин
>
> **Формат:** самостійна практична робота, викладач консультує та приймає результат
>
> **Результат:** курсант створює Swarm, розгортає сервіс із кількох реплік, перевіряє відновлення після відмови задачі та пояснює межі відмовостійкості одно-вузлового кластера.

## Навчальні питання

1. Створення Docker Swarm кластеру.
2. Розгортання сервісу у Docker Swarm.
3. Перевірка відмовостійкості сервісу.

## Мета заняття

Після заняття курсант може:

- пояснити ролі manager і worker, а також різницю між сервісом і його задачами (tasks);
- ініціалізувати Swarm і приєднати до нього вузли;
- розгорнути сервіс із заданою кількістю реплік та перевірити його стан;
- пояснити, як Swarm відновлює бажану кількість задач після відмови контейнера;
- розрізнити відновлення задачі й відмовостійкість до втрати вузла;
- видалити стек і безпечно вивести власний тестовий вузол зі Swarm.

## Необхідні умови

- Запущений Docker Engine або Docker Desktop із доступною командою `docker`.
- Для базової роботи достатньо одного вузла. Docker Desktop запускає Docker Engine у Linux-віртуальній машині; Swarm-кластер на одному ноутбуці не є кластером із незалежними фізичними вузлами.
- Для перевірки відмови вузла потрібні щонайменше два доступні вузли. Для навчальної симуляції відмови worker достатньо менеджера і двох worker-вузлів.
- Контейнери вузлів мають мати мережевий зв'язок між собою. У реальному кластері відкрийте між вузлами TCP `2377`, TCP/UDP `7946` і UDP `4789`; не виставляйте ці порти у публічний інтернет.

У цьому занятті розгортається демонстраційний NGINX зі стандартного Docker Hub, тому збирати та публікувати власний образ не потрібно. Файл `stack.yaml` описує три репліки сервісу та публікує його на порту `8089`.

## Коротко про Swarm

Docker Swarm — вбудований у Docker Engine режим оркестрації. Менеджер зберігає бажаний стан кластера та узгоджує роботу сервісів. Worker-вузли запускають призначені їм задачі. Сервіс описує бажану конфігурацію, а задача — конкретний екземпляр контейнера, який Swarm намагається підтримувати.

```text
Користувач задає сервіс: 3 репліки
                 │
                 ▼
          Swarm manager
          ┌──────┼──────┐
          ▼      ▼      ▼
        task 1  task 2  task 3
```

Якщо контейнер задачі завершується, Swarm створює заміну, щоб повернути сервіс до бажаної кількості реплік. Репліки на одному вузлі не захищають від відмови цього вузла. Для стійкості до втрати вузла задачі мають бути розміщені на інших доступних вузлах, а сам кластер — мати достатньо менеджерів для кворуму. Для production зазвичай використовують непарну кількість менеджерів, наприклад три.

## Практична робота

### Частина 1. Ініціалізація Swarm

Перейдіть до каталогу заняття та перевірте Docker:

```bash
cd Lesson2_9
docker version
docker info --format '{{.Swarm.LocalNodeState}}'
```

Якщо результат останньої команди — `inactive`, ініціалізуйте Swarm:

```bash
docker swarm init
docker info --format '{{.Swarm.LocalNodeState}}'
docker node ls
```

Очікуваний стан — `active`, а `docker node ls` має показати поточний вузол зі статусом `Ready` і роллю `Leader`. Якщо Docker вимагає адресу для оголошення вузла, повторіть ініціалізацію з адресою мережевого інтерфейсу, доступною іншим вузлам:

```bash
docker swarm init --advertise-addr <IP-адреса-менеджера>
```

Для багатовузлового кластера на менеджері отримайте команду приєднання worker:

```bash
docker swarm join-token worker
```

Виконайте показану команду `docker swarm join ...` на кожному окремому вузлі. Не публікуйте join-токен у звіті або відкритому репозиторії: ним можна приєднати вузол до кластера. Після приєднання перевірте вузли на менеджері:

```bash
docker node ls
```

> Якщо Swarm уже активний, не виконуйте повторно `docker swarm init`. Перевірте, чи це ваш навчальний кластер і чи дозволено в ньому створювати сервіси.

### Частина 2. Розгортання сервісу

Перевірте синтаксис і результат розгортання стека:

```bash
docker stack config --compose-file stack.yaml
docker stack deploy --compose-file stack.yaml lesson9
```

Перевірте стек, сервіс і задачі:

```bash
docker stack services lesson9
docker service ps lesson9_web
docker service inspect --pretty lesson9_web
```

Дочекайтеся, поки у сервісу буде `3/3` репліки та задачі перейдуть у стан `Running`. Надішліть кілька запитів:

```bash
curl --fail http://localhost:8089/
```

Відкрийте `http://localhost:8089` у браузері. У Swarm ingress routing mesh опублікований порт доступний через вузол кластера, навіть якщо задача сервісу запущена на іншому вузлі.

Перегляньте логи та стан розміщення задач:

```bash
docker service logs lesson9_web
docker service ps --no-trunc lesson9_web
```

У колонці `NODE` видно, на яких вузлах розміщені задачі. У кластері з одним вузлом усі три репліки неминуче працюють на одному вузлі.

### Частина 3. Перевірка відмовостійкості

Переконайтеся, що сервіс має три активні задачі, і запам'ятайте їхні `NAME` та `NODE`:

```bash
docker service ps lesson9_web
```

В одному терміналі спостерігайте за станом сервісу:

```bash
docker service ps --no-trunc lesson9_web
```

Виберіть активну задачу та її вузол за колонкою `NODE`. На цьому вузлі (а не обов'язково на менеджері) знайдіть контейнер задачі та примусово завершіть його. Підставте фактичний ID з `docker ps`:

```bash
docker ps --filter label=com.docker.swarm.service.name=lesson9_web
docker kill <container-id>
```

Якщо задача розміщена на іншому вузлі, виконайте ці дві команди на ньому або перемкніть Docker CLI на цей вузол. `docker ps` показує контейнери лише того Docker Engine, до якого зараз під'єднаний CLI.

Поверніться до першого термінала. Swarm має позначити стару задачу як завершену та запустити заміну. Перевірте сервіс і доступність HTTP:

```bash
docker service ps lesson9_web
docker stack services lesson9
curl --fail http://localhost:8089/
```

Зафіксуйте стару завершену задачу, нову задачу у стані `Running` і відновлену кількість `3/3`. Заміна може потребувати кількох секунд.

#### Додаткова перевірка: відмова вузла

Цю перевірку виконуйте лише у власному багатовузловому кластері щонайменше з менеджером і двома worker-вузлами. Виберіть worker, на якому є одна або кілька задач сервісу:

```bash
docker node ls
docker service ps lesson9_web
```

На менеджері переведіть вибраний worker у стан `Drain`:

```bash
docker node update --availability drain <ім'я-worker-вузла>
```

Перевірте, що Swarm переносить його задачі на доступні вузли та сервіс знову має три репліки:

```bash
docker node ls
docker service ps lesson9_web
docker stack services lesson9
curl --fail http://localhost:8089/
```

`Drain` — контрольоване обслуговування вузла, а не аварійне вимкнення. Після перевірки поверніть його у робочий стан:

```bash
docker node update --availability active <ім'я-worker-вузла>
```

Не вимикайте менеджер навмання: втрата кворуму може позбавити кластер можливості керувати сервісами. На одному вузлі або без доступних вузлів для перепланування перевірка відмови вузла не доводить відмовостійкість до такої відмови.

## Самостійне завдання

1. Ініціалізуйте власний Swarm або підтвердьте, що наданий викладачем Swarm активний.
2. Розгорніть стек `lesson9` із `stack.yaml`, перевірте конфігурацію та дочекайтеся `3/3`.
3. Відкрийте сервіс у браузері та виконайте HTTP-запит командою `curl`.
4. Покажіть викладачу, на якому вузлі розміщено кожну задачу.
5. Примусово завершіть одну задачу, дочекайтеся заміни та повторно перевірте сервіс і HTTP.
6. Поясніть, які саме відмови перевірено у вашому середовищі, а які — ні.
7. Якщо є багатовузловий кластер, виконайте додаткову перевірку з `drain` і поверніть вузол у стан `active`.
8. Видаліть стек та перевірте, що сервісів заняття більше немає.

| № | Результат | Бали |

| 1 | Ініціалізує Swarm або коректно перевіряє наданий кластер; пояснює роль manager і worker | 1 |
| 2 | Перевіряє YAML і розгортає стек `lesson9` без помилок | 1 |
| 3 | Показує три активні репліки та пояснює відповідність сервісу й задач | 1 |
| 4 | Відкриває сервіс на `localhost:8089` і підтверджує його роботу HTTP-запитом | 1 |
| 5 | Завершує задачу, показує її заміну та відновлення бажаних `3/3` реплік | 1,5 |
| 6 | Точно пояснює різницю між відмовою контейнера й відмовою вузла; не називає одно-вузловий тест перевіркою вузлової відмовостійкості | 1,5 |
| 7 | Для багатовузлового кластера показує перенесення задач після `drain` і повертає вузол у `active` | 1 |

Відсутність багатовузлового середовища не позбавляє балів за пункт 7: курсант пояснює, чому таку перевірку не можна виконати на одному вузлі.

## Прибирання

Після прийняття роботи видаліть лише стек, створений для цього заняття:

```bash
docker stack rm lesson9
docker stack services lesson9
```

Дочекайтеся, поки `lesson9_web` зникне зі списку сервісів. Якщо ви самостійно створили окремий навчальний Swarm і він більше не потрібен, виведіть поточний вузол з нього:

```bash
docker swarm leave --force
```

Не залишайте Swarm, якщо на вузлі працюють інші сервіси або кластер наданий викладачем. Для власного багатовузлового кластера спочатку виведіть worker-вузли зі Swarm, потім виводьте менеджери відповідно до плану викладача.
